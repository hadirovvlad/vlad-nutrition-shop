# VLAD NUTRITION — інтернет-магазин спортивного харчування

Працюючий e-commerce MVP: frontend + backend + база даних + автентифікація +
role-based access control. Не макет — усі сценарії з техзавдання виконуються
через інтерфейс і через API.

Belok.ua використано лише як референс структури та функціональності. Дизайн,
тексти, назва та айдентика — власні.

## Швидкий старт

Потрібен **Node.js 20+** (перевірено на 24.19.0). Більше нічого — ні Docker, ні
окремої СУБД.

```bash
git clone https://github.com/hadirovvlad/vlad-nutrition-shop.git
cd vlad-nutrition-shop
npm install              # встановлює concurrently для запуску обох частин
npm run setup            # ставить залежності client + server, створює й наповнює БД
npm run dev              # API на :4000, сайт на :5173
```

Відкрийте <http://localhost:5173>.

Якщо щось пішло не так, кроки можна виконати окремо:

```bash
npm --prefix server install
npm --prefix client install
npm --prefix server run db:init     # prisma db push + seed
npm --prefix server run dev         # тільки API
npm --prefix client run dev         # тільки frontend
```

`server/.env` уже створений з робочими значеннями для локальної розробки.
Перед публікацією обов’язково замініть `JWT_SECRET` (див. `server/.env.example`).

### Production-збірка

```bash
npm run build            # tsc + vite build + prisma generate
NODE_ENV=production npm start
```

У production-режимі Express роздає готову збірку з `client/dist`, тому все
працює з одного порту (`:4000`) і CORS не потрібен.

## Демо-доступи

Створюються сідером. Паролі змінюються через `server/.env`.

| Роль | Email | Пароль |
| --- | --- | --- |
| Адміністратор | `admin@vladnutrition.ua` | `Admin1234` |
| Менеджер | `manager@vladnutrition.ua` | `Manager1234` |
| Клієнт | `client@vladnutrition.ua` | `Client1234` |

На сторінці входу в dev-режимі ці доступи можна підставити одним кліком.

Після сідування в базі: 14 категорій + 7 підкатегорій, 12 брендів, 48 товарів,
12 замовлень у різних статусах, відгуки, адреси доставки.

## Назва магазину

Назва зібрана у двох константах, тому перейменування — це дві правки:

- `client/src/lib/constants.ts` → `SHOP_NAME`, `SHOP_DOMAIN`
- `server/src/lib/constants.ts` → `SHOP_NAME`, `SHOP_DOMAIN`

Звідси назва розходиться в заголовки сторінок (`useDocumentMeta` додає її
автоматично), логотип, футер, SEO-поля товарів, демо-доступи та власний бренд
магазину в сідері. Окремо, вручну, лишаються файли, які не читають константи:
`client/index.html`, `client/public/favicon.svg`, `client/public/og-image.svg`
та `server/.env`.

> Якщо разом із назвою змінити `AUTH_COOKIE` або ключі `vlad-cart` /
> `vlad-favorites`, усі активні сесії та збережені кошики скинуться. Для
> проєкту без живих користувачів це нормально; на працюючому магазині назви
> краще залишити як є.

## Стек

**Frontend** — React 19, TypeScript, Vite 6, Tailwind CSS 4, React Router 7,
TanStack Query 5, Zustand 5, lucide-react.

**Backend** — Node.js, Express 4, TypeScript, Prisma 6, zod, bcryptjs,
jsonwebtoken, helmet, express-rate-limit, multer.

**База даних** — SQLite за замовчуванням (нуль налаштувань), повністю готова до
переходу на PostgreSQL — див. [розділ нижче](#перехід-на-postgresql).

UI-компоненти написані вручну в стилістиці shadcn/ui (Tailwind + композиція,
`cn()` на `clsx` + `tailwind-merge`), без залежності від CLI-генератора.

## Ролі та права доступу

Три роли: `ADMIN`, `MANAGER`, `CLIENT`.

Ключовий принцип: **права перевіряються на сервері, а не в інтерфейсі**.
Приховати пункт меню недостатньо, тому кожен маршрут проходить через
`requireAuth` → `requireRole(...)`, а роль перечитується з бази на кожному
запиті (зміна роли чи деактивація акаунта діють одразу, а не після протермінації
токена).

### Клієнт

Реєстрація, вхід, каталог, пошук, фільтри, сторінка товару, обране, кошик,
checkout, історія та статуси замовлень, редагування особистих даних, адреси
доставки, зміна пароля, відгуки.

Кабінет: **Мої дані · Мої замовлення · Обране · Адреси доставки · Налаштування ·
Вихід** (`/account`).

### Менеджер (`/manager`)

Дозволено: дашборд зі статистикою, усі замовлення, зміна статусу, редагування
даних замовлення, внутрішні коментарі, картки клієнтів, зв’язок із клієнтом
(клікабельні телефон і email), склад, зміна ціни та наявності, створення знижок.

Заборонено (403 на сервері, не лише приховано в UI):

| Дія | Поведінка |
| --- | --- |
| Створити/видалити менеджера | `403` |
| Побачити список персоналу | `403` |
| Системні налаштування | `403` |
| Видалити товар | `403` + можливість надіслати запит адміну |
| Повне редагування товару | `403` (доступні лише ціна, стара ціна, залишок, видимість) |
| Модерація відгуків | читання дозволено, видалення — `403` |

Запит на видалення приховує товар з каталогу й підсвічується адміністратору
окремим блоком на сторінці товарів.

### Адміністратор (`/admin`)

Повний доступ. Dashboard: кількість замовлень, розподіл за статусами, оборот,
середній чек, кількість клієнтів і товарів, товари що закінчуються,
найпопулярніші товари, графік обороту за 14 днів, останні замовлення.

Навігація: **Dashboard · Замовлення · Товари · Категорії · Бренди · Клієнти ·
Менеджери · Склад · Акції · Відгуки · Налаштування**.

### Запобіжники

- Роль ніколи не береться з тіла запиту — реєстрація завжди створює `CLIENT`.
- Адміністратора не можна видалити через панель.
- Не можна знизити власну роль або залишити систему без активного адміна.
- Користувача, пов’язаного із замовленнями, деактивують, а не видаляють, щоб не
  зламати історію.
- Товар, що присутній у замовленнях, переходить в архів замість видалення.
- Замовлення клієнта читаються запитом із `userId` в умові, тому підбір `id`
  чужого замовлення повертає `404`.
- Внутрішні коментарі менеджерів не потрапляють у відповіді клієнтського API.

## API

Базовий префікс `/api`. Тіла запитів валідуються zod; помилки повертаються як
`{ message, details: [{ path, message }] }`, і клієнт розкладає їх під поля форм.

### Публічне

| Метод | Шлях | Опис |
| --- | --- | --- |
| `GET` | `/catalog/home` | всі секції головної одним запитом |
| `GET` | `/catalog/products` | каталог: фільтри, сортування, пагінація |
| `GET` | `/catalog/products/:slug` | товар + відгуки + схожі товари |
| `GET` | `/catalog/search?q=` | live-пошук: товари, категорії, бренди |
| `GET` | `/catalog/categories`, `/catalog/categories/:slug` | дерево категорій |
| `GET` | `/catalog/brands`, `/catalog/goals` | бренди, цілі |
| `GET` | `/catalog/filters` | значення для сайдбару фільтрів |
| `POST` | `/orders` | оформлення (працює і для гостя) |
| `GET` | `/orders/confirmation/:number` | сторінка «замовлення створено» |

Параметри `/catalog/products`: `q`, `category`, `brand`, `goal`, `weight`,
`flavor`, `form`, `minPrice`, `maxPrice`, `minRating`, `minDiscount`, `inStock`,
`onSale`, `isNew`, `isBestseller`, `sort`, `page`, `limit`. Списки передаються
через кому. Сортування: `popular`, `new`, `price-asc`, `price-desc`, `rating`,
`discount`.

Фільтр за категорією включає її підкатегорії, тому `/catalog/protein` показує
весь розділ. Невідомий slug дає нуль результатів, а не «все».

### Автентифікація

`POST /auth/register` · `POST /auth/login` · `POST /auth/logout` ·
`GET /auth/me` · `POST /auth/forgot-password` · `POST /auth/reset-password` ·
`POST /auth/change-password`

### Кабінет клієнта (потрібен вхід)

`PUT /account/profile` · `GET|POST|PUT|DELETE /account/addresses[/:id]` ·
`GET /account/favorites` · `POST|DELETE /account/favorites/:productId` ·
`GET /account/orders` · `GET /account/orders/:id` · `POST /reviews`

### Панелі (`/api/mgmt/*`, потрібні `ADMIN` або `MANAGER`)

Один namespace для обох панелей із перевіркою прав на кожному маршруті:
`stats`, `orders`, `products`, `users`, `reviews`, `settings`, `uploads`,
`categories`, `brands`. Маршрути, що вимагають `ADMIN`, позначені в
[таблиці прав](#менеджер-manager) вище.

Окремо варто відзначити:

- `PATCH /mgmt/products/:id/inline` — єдина мутація товару, доступна менеджеру
  (ціна, стара ціна, залишок, видимість).
- `POST /mgmt/products/bulk-discount` — знижка на вибрані товари, категорію або
  бренд. Рахується завжди від початкової ціни, тому повторне застосування не
  накопичується, а `percent: 0` повертає початкову ціну.
- `PATCH /mgmt/orders/:id/status` — зміна статусу; скасування повертає товари на
  склад, а автор зміни стає менеджером замовлення.

## Модель даних

`users`, `addresses`, `categories` (self-relation, один рівень підкатегорій),
`brands`, `products`, `orders`, `order_items`, `order_notes`, `reviews`,
`favorites`, `settings`.

Рішення, які варто знати:

- **Ціни** зберігаються як `Float` у гривнях і округлюються до 2 знаків на
  кожному записі (`lib/money.ts`). Ціна замовлення завжди рахується на сервері
  з бази — значення з тіла запиту ігноруються.
- **`OrderItem` містить знімок товару** (назва, ціна, зображення, вага, смак),
  тому історія залишається читабельною після перейменування або видалення
  товару.
- **`Order.number`** — людський номер, що починається з 1048 (як у ТЗ).
- **`discountPercent` і `searchIndex`** денормалізовані та оновлюються на кожному
  записі: перше дає сортування за розміром знижки на боці БД, друге робить
  пошук робочим для української мови (SQLite `LIKE` нечутливий до регістру лише
  для ASCII, тому порівнюється lowercase з lowercase).
- **Списки** (`weights`, `flavors`, `goals`, `images`, `specs`) зберігаються як
  JSON-текст — SQLite не має ні масивів, ні `Json`. Розбір зосереджений у
  `lib/json.ts`, тому зламаний рядок не роняє запит.
- **Enum-подібні значення** (роль, статус, спосіб доставки й оплати) —
  `String` + zod, бо Prisma не підтримує `enum` на SQLite. Список — у
  `lib/constants.ts`.

## Безпека

- Пароли хешуються `bcrypt` (12 раундів). У відкритому вигляді не зберігаються
  і ніколи не повертаються з API.
- JWT у **httpOnly-cookie** (`sameSite=lax`, `secure` у production) — токен
  недоступний зі JavaScript, тому XSS не дає його викрасти. `Authorization:
  Bearer` також підтримується для інтеграцій.
- Перевірка ролей **на backend** на кожному маршруті; роль перечитується з БД.
- Валідація всіх форм і всіх тіл запитів через zod, з поверненням помилок
  по полях.
- SQL-інʼєкції неможливі: усі запити йдуть через Prisma з параметризацією.
- XSS: React екранує весь вивід, `dangerouslySetInnerHTML` не використовується.
- `helmet`, CORS з білим списком origin, rate limiting (жорсткіший на
  `/api/auth/*`).
- Відновлення пароля: у БД лежить лише SHA-256 хеш токена, термін дії 1 година,
  токен одноразовий.
- Немає account enumeration: невірний email і невірний пароль дають однакову
  відповідь, `forgot-password` відповідає однаково для існуючого й неіснуючого
  email.
- Завантаження файлів: білий список MIME-типів, ліміт 5 МБ, імʼя файлу
  генерується сервером (імʼя з клієнта не використовується).
- Сервер відмовляється стартувати в production із дефолтним `JWT_SECRET`.

> Поштового сервісу в MVP немає. Щоб потік відновлення пароля можна було
> пройти цілком, **поза production** токен повертається у відповіді
> (`devToken`). Перед запуском підключіть надсилання листа і приберіть це поле.

## Деплой на Render

У репозиторії є `render.yaml`, тому розгортання робиться кількома кліками:

1. [dashboard.render.com](https://dashboard.render.com) → **New +** → **Blueprint**.
2. Підключити GitHub і вибрати репозиторій `vlad-nutrition-shop`.
3. Render прочитає `render.yaml` і покаже web-сервіс + базу PostgreSQL.
4. Заповнити три змінні, які навмисно не зберігаються в репозиторії:
   `SEED_ADMIN_PASSWORD`, `SEED_MANAGER_PASSWORD`, `SEED_CLIENT_PASSWORD`.
5. **Apply**. Перший деплой триває 5–10 хвилин.

Адреса вигляду `https://vlad-nutrition.onrender.com` з’явиться в дашборді.

Що відбувається під час збірки: `DATABASE_PROVIDER=postgresql` перемикає
провайдер Prisma, `prisma db push` створює схему, а сід наповнює базу
демо-даними **лише якщо вона порожня** (`SEED_ONLY_IF_EMPTY=true`), тому
наступні деплої не стирають реальні замовлення. `JWT_SECRET` Render генерує сам
і зберігає між деплоями.

Обмеження безкоштовного тарифу, про які варто знати:

- Сервіс засинає після ~15 хвилин без запитів, і перше відкриття після сну
  триває до хвилини.
- Диск ефемерний: завантажені через адмінку фотографії зникнуть після
  перезапуску. Згенеровані зображення товарів не залежать від диска й
  працюють завжди — для постійного зберігання фото потрібен S3 або Cloudinary.
- Безкоштовна база PostgreSQL на Render має обмежений термін життя; для
  тривалого проєкту варто перейти на платний план або зовнішній Postgres.

> Демо-паролі з розділу [Демо-доступи](#демо-доступи) діють лише локально. На
> публічному сайті задайте інші — інакше будь-хто, хто прочитає цей README,
> зайде у вашу адмін-панель.

## Перехід на PostgreSQL

Провайдер Prisma не читає `env()`, тому його переписує скрипт
`server/scripts/db-provider.mjs` перед будь-якою командою prisma. Схема при
цьому лишається одна — без двох файлів, що розходяться.

У `server/.env`:

```ini
DATABASE_PROVIDER=postgresql
DATABASE_URL="postgresql://user:pass@host:5432/vlad_nutrition?schema=public"
```

Далі `npm --prefix server run db:push && npm --prefix server run db:seed`.
Щоб повернутися на SQLite, поставте `DATABASE_PROVIDER=sqlite` — рядок у схемі
перепишеться назад.

Усі поля схеми Postgres-сумісні. Після переходу можна за бажанням:
перевести `String`-поля ролі та статусів на справжні `enum`, а JSON-текстові
колонки — на `Json`/`String[]`, замінивши хелпери в `lib/json.ts`. Обовʼязково
для роботи це не потрібно.

## Зображення товарів

У ТЗ згадано Cloudinary, але MVP не залежить від зовнішнього акаунта:

1. **Згенеровані візуали.** Товар без фото отримує детерміновану SVG-ілюстрацію
   (`components/product/ProductVisual.tsx`): силуєт вибирається за формою
   випуску (банка, бутель, флакон із капсулами, батончик, шейкер, футболка,
   аксесуар), а колір — за хешем slug. Один і той самий товар завжди виглядає
   однаково, каталог виглядає оформленим, і нічого не потрібно завантажувати.
2. **Реальні фото.** Адмін завантажує файли (`POST /mgmt/uploads/images`, локальне
   сховище `server/uploads`, роздається статично) або вставляє готовий URL.
3. **Fallback.** Якщо зображення не завантажилось, компонент показує згенерований
   візуал замість «битої» картинки.

Щоб перейти на Cloudinary, достатньо замінити один обробник —
`server/src/modules/mgmt/uploads.routes.ts`.

## Що зроблено за критеріями готовності

| № | Критерій | Де перевірити |
| --- | --- | --- |
| 1 | Користувач може зареєструватися | `/register` |
| 2 | Користувач може увійти | `/login` |
| 3 | Користувач може знайти товар | пошук у шапці (`creatine`, `протеїн`), фільтри каталогу |
| 4 | Може додати товар у кошик | картка товару, швидкий перегляд, сторінка товару |
| 5 | Може оформити замовлення | `/checkout` → `/order/:number` |
| 6 | Менеджер бачить замовлення | `/manager/orders` |
| 7 | Менеджер може змінити статус | `/manager/orders/:id` |
| 8 | Адмін може створити товар | `/admin/products/new` |
| 9 | Новий товар у каталозі | зʼявляється одразу, індексується пошуком |
| 10 | Роли та права працюють | таблиця прав вище |
| 11 | Адаптив під телефон | 375 / 768 / 1440 / 1920; hamburger, bottom nav, фільтри окремою панеллю, 2 картки в ряд |
| 12 | Сучасний дизайн | `#F7F7F7` фон, `#111111` текст, лаймовий акцент, обмежена палітра |
| 13 | RBAC не обходиться через URL або API | клієнтський guard **і** перевірка на сервері |
| 14 | Loading / error / empty states | скелетони, `ErrorState` з повтором, `EmptyState` на кожному списку |

Додатково реалізовано: автоматичний розрахунок знижки, масові знижки за
категорією чи брендом, внутрішні коментарі до замовлень, запити менеджера на
видалення товару, модерація відгуків, налаштування магазину, повторне
замовлення в один клік, SEO-поля з дефолтами (title, description, slug, H1,
Open Graph), sticky-хедер, toast-повідомлення, skeleton-завантаження.

## Чого свідомо немає в MVP

Згідно з розділом «Що НЕ потрібно» техзавдання: складної CRM, системи бонусів,
мобільного застосунку, складної аналітики, надмірних анімацій.

Що варто додати перед реальним запуском:

- надсилання листів (відновлення пароля, підтвердження замовлення);
- платіжний шлюз — «онлайн-оплата» зараз фіксує спосіб оплати, але не проводить
  транзакцію;
- інтеграція з API Нової Пошти для довідника міст і відділень (зараз це текстові
  поля);
- автоматичні тести (наявний сценарій перевірявся вручну та скриптом по API);
- перенесення зображень у CDN.
